# Feature Specification: 加入管理时自动上报会话最后文本

**Feature Branch**: `fix/080-session-manage-auto-report`

**Created**: 2026-11-27

**Status**: Approved

**Input**: User description: "修复 bug：按预期，一个未管理的会话被加入管理（session_manage）时，应自动把该会话最后一段 text 作为 report 发给调度会话，代码逻辑应与其余被管理会话的自动上报（turn_end 自动报告）一致。当前加入管理时没有发生这一自动上报。请定位原因并修复。"

## Open Decisions

无。

## Clarifications

### Session 2026-11-27

- [D-001] Q: 上报正文取会话的哪段文本 -> A: 取最后轮次中最后一条含非空文本的助手消息，按轮次自动上报的规则拼接其全部文本块。
- [D-002] Q: 上报的来源标记 -> A: 沿用 `turn_end`，调度提示词与文档的来源说明保持不变。
- [D-003] Q: 目标会话轮次仍在运行或仍有运行中的子代理时是否上报 -> A: 都跳过；运行中的轮次结束时会由轮次自动上报补上这一条。
- [D-004] Q: 会话没有助手文本或文本为空白时如何处理 -> A: 静默跳过，不存档也不投递，接管照常成功。
- [D-005] Q: 上报投递失败时接管的结果 -> A: 接管照常成功，投递失败只写日志。
- [D-006] Q: 先管理、取消管理后再次管理时是否再次上报同一条文本 -> A: 再次上报；是否已上报按任务标识区分，不按内容去重。
- [D-007] Q: `session_manage` 的工具结果是否新增字段 -> A: 保持不变，只返回 `sessionId`、`taskId`、`title`。
- [D-008] Q: 接管上报与轮次结束自动上报是否可能对同一轮次同时触发 -> A: 会。轮次结束处理会异步读取任务，接管可能在它之前建立任务，两者都会判定该轮未上报并各投递一次。系统按会话串行判定这两种上报，并记录某轮已投递到哪个任务，使接管那一刻最多产生一条上报。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 接管已有会话时补发其最后进展 (Priority: P1)

用户此前在网页里和一个会话完成了工作，该会话从未被管理。用户要求调度会话接管这个会话。接管成功后，调度会话收到该会话最后一段助手文本作为一份进度上报，无需用户复述。

**Why this priority**: 这是本次缺陷本身。没有这次上报，调度会话接管后不知道会话已有的结论，用户必须再描述一遍。

**Independent Test**: 让一个未管理会话完成一轮并留下助手文本，对其执行 `session_manage`。调度会话收到一条 `progress` 上报，正文等于该会话最后一段文本，来源与轮次结束自动上报相同。

**Acceptance Scenarios**:

1. **Given** 一个未管理、已完成轮次且最后助手文本为 `T` 的会话，**When** 调度会话对其调用 `session_manage`，**Then** 任务被建立，并投递一条正文为 `T` 的 `progress` 上报，来源为 `turn_end`。
2. **Given** 被管理会话在接管后继续正常结束轮次，**When** 轮次结束，**Then** 自动上报照常发生；接管时的上报不抑制后续轮次。
3. **Given** 接管时的上报已投递，**When** 查看任务台账，**Then** 任务状态不变，上报不结束任务。

---

### User Story 2 - 接管与轮次结束不重复上报同一轮 (Priority: P1)

会话最后一轮刚好在接管前后结束时，调度会话只收到一条该轮文本的上报。

**Why this priority**: 同一句话重复投递会让调度会话重复转述，用户收到重复通知。

**Independent Test**: 在轮次结束事件处理的同一时刻执行 `session_manage`，让任务在轮次结束处理读取任务之前建立。断言该轮文本只产生一条上报。

**Acceptance Scenarios**:

1. **Given** 目标会话的最后一轮正在结束，**When** 该轮结束时已被接管，**Then** 该轮文本恰好产生一条上报，无论由接管还是轮次结束触发。
2. **Given** 目标会话的轮次仍在运行，**When** 执行 `session_manage`，**Then** 接管不投递上报；该轮正常结束时由轮次自动上报投递一条。
3. **Given** 最后一次接管已把某轮文本投递给调度会话，**When** 用户取消管理后再次管理该会话，**Then** 建立新任务并再次上报该文本。

---

### User Story 3 - 无内容的接管不产生噪声 (Priority: P2)

用户接管一个没有助手文本、仍是空白输出或最后一轮异常结束的会话。接管成功，调度会话不会收到空的、空白的或异常轮次的上报。

**Why this priority**: 无意义的上报会让调度会话做不必要的转述与重发请求。

**Independent Test**: 对没有助手消息、最后文本为空白、最后一轮以错误或取消结束的会话分别执行 `session_manage`，任务建立成功，不产生上报。

**Acceptance Scenarios**:

1. **Given** 会话没有任何助手消息，**When** 调用 `session_manage`，**Then** 任务建立成功，不产生上报。
2. **Given** 会话最后助手文本只含空白字符，**When** 调用 `session_manage`，**Then** 任务建立成功，不产生上报。
3. **Given** 最后一轮以错误或取消结束，**When** 调用 `session_manage`，**Then** 不产生上报；错误轮次沿用失败通知。
4. **Given** 最后一轮已调用过 `send_report`，**When** 调用 `session_manage`，**Then** 不产生接管上报。

---

### User Story 4 - 上报失败不影响接管 (Priority: P3)

接管时的上报投递失败时，会话仍被管理，调度会话仍能从工具结果知道接管成功。

**Why this priority**: 接管是用户明确要求的动作，投递失败是次要问题。

**Independent Test**: 让上报投递失败，执行 `session_manage`；工具返回成功，任务存在，日志记录一次投递失败。

**Acceptance Scenarios**:

1. **Given** 调度会话不可达，**When** 调用 `session_manage` 且会话有最后文本，**Then** `session_manage` 成功返回，任务存在，失败只写日志。

---

### Edge Cases

- 最后一条助手消息含多个文本块：按轮次自动上报的规则拼接。
- 最后一条事件不是助手消息：取最后轮次中最后一条有非空文本的助手消息。
- 同一会话重复 `session_manage`：保留现有「已管理」错误，不产生上报。
- 会话在 `session_manage` 之前已被归档或不存在：保留现有错误行为，不产生上报。
- 上报存档成功但投递失败：保留存档，接管成功，只写日志。
- 插件加载前已结束的轮次：没有接管上报。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 对一个未被管理、已存在且不是调度会话的会话执行 `session_manage` 时，系统 MUST 在建立任务后，把该会话最后轮次的最后文本作为 `progress` 上报投递给调度会话。
- **FR-002**: 上报正文 MUST 与轮次结束自动上报取文本的规则一致：最后轮次中最后一条非空助手消息的全部文本块，按行拼接。
- **FR-003**: 接管上报 MUST 通过与被管理会话 `send_report`、轮次结束自动上报相同的存档与投递路径完成，来源记为 `turn_end`。
- **FR-004**: 接管上报 MUST NOT 结束任务，也不改变任务状态。
- **FR-005**: 以下情形系统 MUST NOT 产生接管上报，且 `session_manage` MUST 照常成功：最后轮次仍在运行、最后一轮不是正常结束、文本为空或空白、最后一轮调用过 `send_report`、仍有运行中的子代理。
- **FR-006**: 上报投递失败时，系统 MUST 保留已建立的任务并照常返回成功，失败只写日志。
- **FR-007**: 接管上报与轮次结束自动上报 MUST 按会话串行判定，使同一轮次的文本在接管那一刻最多产生一条上报。
- **FR-008**: 同一会话再次管理时，新任务 MUST 再次收到最后轮次的文本上报；判定是否已上报 MUST 按任务标识区分，不按正文内容去重。
- **FR-009**: 已管理会话、调度会话与不存在会话的 `session_manage` 错误行为 MUST 保持不变。
- **FR-010**: `session_manage` 的工具结果 MUST 保持现有字段 `sessionId`、`taskId`、`title`。
- **FR-011**: 接管上报 MUST NOT 影响该会话后续轮次的自动上报判断。
- **FR-012**: 调度提示词与机制文档对上报来源的说明 MUST 保持现有 `turn_end` 含义。

### Key Entities *(include if feature involves data)*

- **会话**: 被接管的已有会话，提供标题、工作目录、轮次状态与助手文本。
- **任务**: 接管时建立的未结束任务，一个会话最多对应一个任务。
- **上报**: 存档的 `progress` 记录，含报告标识、`kind`、`origin`、正文与投递状态。
- **最后轮次状态**: 会话最近一轮的结束原因、是否调用过 `send_report`、最后文本与已投递的任务标识。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对 100% 的「有最后助手文本且满足条件」的未管理会话执行 `session_manage`，调度会话在下一步收到恰好一条正文等于该文本的 `progress` 上报。
- **SC-002**: 对 100% 的抑制场景执行 `session_manage`，产生 0 条接管上报。
- **SC-003**: `session_manage` 的成功与失败结果在修复前后保持一致，错误信息不变。
- **SC-004**: 每个被接管会话在每个任务上最多产生一条接管上报。
- **SC-005**: 在接管与轮次结束并发的测试样本中，同一轮文本产生 1 条上报的比例为 100%。
- **SC-006**: 同一会话再次管理后，新任务收到该文本的 1 条上报。

## Assumptions

- 插件观察会话的轮次事件，接管时重放最后轮次的判定条件；插件加载前已结束的轮次不补发。
- 接管时上报的送达与唤醒方式与轮次结束自动上报相同。
- 修复范围限于接管入口与共享的轮次上报判定，不改动任务与上报的存档格式。
- 助手消息文本拼接沿用现有轮次自动上报的规则。
