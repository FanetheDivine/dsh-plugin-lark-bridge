# Feature Specification: 调度会话响应策略与上报投递

**Feature Branch**: `feat/069-dispatch-response-policy`

**Created**: 2026-11-26

**Status**: Approved

**Change Category**: 插件变更

**Input**: User description: "1) 改调度提示词：下发指令后立刻响应用户。说明任务会话的报告分「自动发（turn_end）」和「主动发（send_report）」两种；若报告没有明确描述当前状态，或没有需用户确认的点（例如最后一个 turn 恰好是 Background 任务汇报了 text，此时该报告只与那段 text 有关），就向任务会话注入消息，让它重发一次报告；其他情况不要干扰任务会话。2) 用户对调度会话的指令不一定转发给任务会话（例如用户说「某任务会话要等某个值，暂时不用动」，这就不应转发）。3) 对用户也一样：只有实际需要汇报或确认时才向用户发消息，不是只要被注入就发。4) send_report 之后，报告总是缓存成文件到调度会话工作区；向调度会话注入时只注入文件（路径），让调度会话自行去读。5) lark_notify 新增推送卡片能力：不是自动推送，由调度会话主动调用；例如报告特别长时放进卡片，平时收起，展开可看完整 Markdown。6) 任务会话发出问题后，用户直接与任务会话交互，调度会话不知道这一点。"

- [D-001] Q: 第 4 点由谁读报告文件？ -> A: 调度会话自行读取。注入块只给路径，调度会话需要内容时自己读文件。
- [D-002] Q: 「需要重发」的判定条件？ -> A: 报告既没有描述任务当前状态，也没有需要用户确认的点时才请求重发。

- [D-004] Q: 重发请求是否设次数上限或兜底？ -> A: 只做主流程，假设模型按预期行为，不做次数上限与兜底。
- [D-005] Q: 不转发的说明性消息如何处理？ -> A: 用 `task_update` 的 `add_message` 记进该任务的消息列表，只记录，不投递。
- [D-006] Q: 每条用户消息是否都要回复？ -> A: 每条都回复，用户发来的内容都有意义。

- [D-008] Q: 卡片形态？ -> A: 常显部分是模型写的一句总结，例如「xxx 任务需要确认」「xxx 已完成」；完整 Markdown 默认收起，展开可读。
- [D-009] Q: 卡片内容超过单条上限时如何处理？ -> A: 按顺序拆成多张卡片，每张都带总结句与序号；整体失败时返回错误，不自动回落为文本。
- [D-010] Q: 卡片模式在 GUI 中如何呈现？ -> A: 沿用通知卡片，显示总结句、完整 Markdown 原文、task id 与任务会话链接。
- [D-011] Q: 上报投递是否补轮次结束兜底？ -> A: 纳入，复用飞书消息注入的同类处理。
- [D-012] Q: 是否新增 `task_send`？ -> A: 不纳入。转发仍分 `task_update` 与 `session_send` 两步。
- [D-013] Q: 用户直接在任务会话中交互，调度会话不知道，如何处理？ -> A: 维护任务日志，在调度会话的 pre-step 注入当前会话还没有的条目，区分全新会话与已有会话。
- [D-014] Q: `lark_notify` 如何关联任务？ -> A: 新增可选 `task_id` 参数，用于按任务分开发送与显示任务标识；任务不存在或已结束时返回错误、不发送。
- [D-015] Q: 按任务分开发送是否也适用于文本模式？ -> A: 适用。同一任务的内容合并为一条，不同任务分开发送，与任务无关的内容单独一条。
- [D-016] Q: 通知如何显示所属任务？ -> A: 飞书卡片标题与文本模式首行写「<title> (<task id>)」。GUI 卡片显示 task id，并链接到该任务的会话。
- [D-017] Q: 未带 `task_id` 的通知在 GUI 卡片中是否显示会话链接？ -> A: 不显示。
- [D-018] Q: 任务会话 id 如何交给 GUI？ -> A: `lark_notify` 执行时按 `task_id` 查台账，把任务会话 id 写进只供 GUI 读取的结果元数据；模型看到的结果只有消息 id。
- [D-019] Q: `lark_notify` 的结果返回什么？ -> A: 只返回消息标识。去掉分段数、回复目标与会话标识；失败时返回错误。
- [D-020] Q: 日志记录哪些事件？ -> A: 只记调度会话看不到的事件：用户在 GUI 直接发给被管理会话的消息，以及用户在 GUI 停止任务会话的轮次。
- [D-021] Q: 用户直接交互后任务会话的回复是否入日志？ -> A: 不入，由 `turn_end` 报告覆盖。
- [D-022] Q: 日志放在哪里？ -> A: 调度工作区 `task-logs/<taskId>.jsonl`，每行一条；任务结束时随任务移到 `archive/<taskId>/`；每条不单独 git 提交，任务归档时一并提交。
- [D-023] Q: 每条日志包含什么？ -> A: 条目 id、时间、taskId、任务会话 id、事件类型与用户原文；原文超过 2000 字符时截断并注明。
- [D-024] Q: 如何判断条目已在当前调度会话中？ -> A: 注入时给消息打上来源标记与条目 id；判断时扫描调度会话的完整事件日志，包括已被压缩的部分。
- [D-025] Q: 全新会话怎么注入？ -> A: 没有收到过日志注入的调度会话视为全新会话。注入一条快照，列出全部未结束任务的标题、状态、工作区与最新报告路径，并附上每个任务在其最新报告之后的日志条目。
- [D-026] Q: 已有会话怎么注入？ -> A: 只注入事件日志中还没有的条目；压缩后不重新注入。
- [D-027] Q: 写日志时是否唤醒空闲的调度会话？ -> A: 不唤醒，在调度会话下一次 pre-step 时注入。
- [D-028] Q: 注入顺序与位置？ -> A: 同一步的条目按时间升序合成一条消息，插在本批第一条消息之前。
- [D-029] Q: 调度会话收到日志条目后怎么处理？ -> A: 不通知用户；等待用户回答的任务收到用户直接消息后，调度会话用 `task_update` 设为 `in_progress`。
- [D-030] Q: 日志与报告存档、台账的关系？ -> A: 三者各自独立：报告存档与注入不变，台账 `task.messages` 记调度会话处理过的用户消息，日志只记 D-020 的事件。

### 审查后的补充决策

- [D-031] Q: 任务名由模型还是插件写？ -> A: 由插件写。带 `task_id` 时标题前缀由插件补写，模型只在正文写内容；调度提示词与桥接提醒 MUST 相应说明，避免两处都写。
- [D-032] Q: 如何区分用户主动停止与插件归档时的取消？ -> A: 只记用户主动停止：轮次以 `user` 取消、且该会话不在归档流程中。写日志前 MUST 在同一工作区队列内确认任务仍是未结束任务，任务已结束时丢弃该条目。
- [D-033] Q: 报告路径在归档后失效如何处理？ -> A: 块内路径相对调度工作区根、以 `/` 分隔，指向 `reports/<taskId>/`。调度提示词 MUST 说明任务归档后报告改在 `archive/<taskId>/reports/`，读取失败时改读该位置。
- [D-034] Q: 是否用「与上次通知重复」判定是否通知？ -> A: 不用。台账没有通知记录，判定改为只看本份报告：含新的结果、里程碑、阻塞、失败或提问时通知，只是确认或复述本次工作的内容时不通知。
- [D-035] Q: 卡片模式的参数是什么？ -> A: `mode` 取 `text`（默认）或 `card`；`card` 模式用 `summary` 传一句总结、用 `text` 传完整 Markdown。单张卡片按飞书卡片 JSON 不超过 30 KB 计，超过时按 Markdown 段落边界拆分。
- [D-036] Q: 台账不可读时 `lark_notify` 如何降级？ -> A: 台账或调度工作区根不可读时，带 `task_id` 的调用返回错误并不发送；不带 `task_id` 的调用照常发送。
- [D-037] Q: 多段或多张发送部分成功后的失败语义？ -> A: 错误说明已发送的张数与第一条消息标识；调度会话 MUST NOT 重发整批，只补发剩余部分或改发一条说明。
- [D-038] Q: 日志条目 id 如何生成？ -> A: 由任务会话 id 与该事件在会话日志中的 seq 派生，同一事件重复观察得到同一条目。
- [D-039] Q: 全新会话标记如何持久化？ -> A: 只依赖调度会话事件日志中的注入标记。没有任何未结束任务时也注入一条空快照，让标记落地。
- [D-040] Q: 日志注入消息是否按用户消息回复？插在哪？ -> A: 日志注入消息、上报块、失败通知与归档通知都不是用户消息，不为它们回复。日志注入消息排在桥接提醒之后、本批第一条 `<lark-message>` 之前。
- [D-041] Q: 改结果文案后 GUI 卡片如何继续显示？ -> A: 卡片匹配器 MUST 同时识别新结果文案与历史结果文案。
- [D-042] Q: 归档后的日志文件名？ -> A: `archive/<taskId>/task-log.jsonl`。

## 现状基线

以下结论均有代码证据：

1. 调度提示词 `src/sa-dispatch/prompt.ts` 没有出现 `lark_notify`。经 `lark_notify` 回复的规则只写在桥接提醒 `src/reminder.ts:15-27`，且围绕 `<lark-message>` 编写。
2. 调度提示词只要求新建任务后告知用户（`prompt.ts:23`）。追加消息、回答提问、接管会话、取消任务都没有回执要求。置顶失败要求「in the same reply」说明（`prompt.ts:60`），回应被推到收尾之后。
3. 用户消息一律视为任务消息：属于未结束任务的消息「Append it with task_update and deliver it with session_send」（`prompt.ts:34`、`prompt.ts:70`）。`prompt.ts:35` 的「Answering a task session works the same way」有歧义。
4. 报告一律转述给用户（`prompt.ts:44-45`），没有按内容取舍的规则。提示词按 `desc` 修正任务标题（`prompt.ts:46`）。
5. 任务会话每个正常结束且未调用 `send_report` 的轮次，都以最后一段助手文本自动上报，`origin="turn_end"`（`src/lark-super-agent/managed/turn-report.ts:109-124`）。后台任务或子代理完成后开启的轮次也会触发，此时文本只与该后台任务有关。
6. `send_report` 与自动上报都已存档到调度工作区：`reports/<taskId>/<reportId>.md` 含 front matter 与正文，附件复制为 `<reportId>-<n>-<文件名>.md`，并做 git 提交（`src/lark-super-agent/reports.ts:149-192`）。
7. 注入调度会话的 `<task_session_message>` 块带完整 `desc`、`text` 与附件副本路径，不带报告文件路径（`src/lark-super-agent/blocks.ts:41-63`、`service.ts:386-405`）。
8. 上报投递直接调用 `agent.steer`（`service.ts:358-364`），没有飞书消息注入所用的轮次结束兜底（`src/sessions.ts:371-381`）。
9. `lark_notify` 只发纯文本，按 15 000 字符分段（`src/tools.ts:113-148`）。
10. 飞书消息到达后逐条立即注入（`src/bridge.ts:268-290`）。`docs/how-it-works.md` 与 `docs/known-risks.md` 仍写着 15 秒静默后整批注入。
11. 提示词与桥接提醒都要求每次提及任务写「<title> (<task id>)」（`prompt.ts:9`、`reminder.ts:24`）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 下发指令后立刻得到回应 (Priority: P1)

用户在飞书给调度会话发一条任务。调度会话创建或通知任务会话后，紧接着用 `lark_notify` 告诉用户已派发到哪个工作区、哪个任务，然后才做置顶等收尾。

**Why this priority**: 用户只能通过飞书看到调度会话的动作。回应排在收尾之后，用户会长时间收不到任何反馈。

**Independent Test**: 在调度会话发一条可派发的任务消息，检查轮次事件：成功的 `session_create` 之后的下一步含 `lark_notify`。

**Acceptance Scenarios**:

1. **Given** 用户发来一条新任务，**When** `session_create` 成功，**Then** 下一步调用 `lark_notify` 告知工作区与任务，`session_pin` 与它同步或在其后执行。
2. **Given** 用户补充一条属于未结束任务的消息，**When** 调度会话把它投递给任务会话，**Then** 投递后的下一步用 `lark_notify` 确认已送达哪个任务。
3. **Given** 用户要求取消任务，**When** `task_end` 成功，**Then** 下一步用 `lark_notify` 确认。
4. **Given** 置顶或归档失败，**When** 调度会话已经回应过用户，**Then** 再发一条简短 `lark_notify` 说明失败。
5. **Given** 通知带 `task_id`，**When** 消息发出，**Then** 任务名由插件写在标题前缀，正文里不再重复。

---

### User Story 2 - 报告不充分时请任务会话重发 (Priority: P1)

任务会话的某一轮恰好是后台任务完成后的收尾，最后一段文本只讲了这个后台任务。自动上报因此没有说清任务整体进展，也没有要用户确认的点。调度会话读到这份报告后，向任务会话发一条消息，请它用 `send_report` 重发一份描述当前状态的报告。其他报告不打扰任务会话。

**Why this priority**: 自动上报只取最后一段文本，内容可能与任务整体无关。调度会话把它原样转给用户会误导用户，直接丢弃又会漏掉进展。

**Independent Test**: 构造一份只描述后台任务输出的 turn_end 报告投给调度会话，检查调度会话向该任务会话发了一次重发请求、没有通知用户；再构造一份描述清楚的报告，检查调度会话没有向任务会话发任何消息。

**Acceptance Scenarios**:

1. **Given** 报告既没有描述任务当前状态，也没有需要用户确认的点，**When** 调度会话处理它，**Then** 向对应任务会话发一次重发请求，请求说明要报告任务当前状态与需要用户确认的点。
2. **Given** 报告充分，**When** 调度会话处理它，**Then** 不向任务会话发送确认、转述或任何其他消息。
3. **Given** 调度会话处理任一报告，**When** 它向任务会话发消息，**Then** 消息只能是重发请求或用户本人的话。

---

### User Story 3 - 只在需要时联系用户 (Priority: P1)

调度会话收到报告或失败通知后，先判断本份报告是否有需要用户知道或确认的内容。有结果、里程碑、阻塞、失败或提问时通知用户；纯噪声不通知。用户发来的每条消息都回复。

**Why this priority**: 每次注入都通知用户会打扰用户，也让重要通知被淹没。

**Independent Test**: 依次投递一份含提问的报告、一份只写「收到」的 turn_end 报告，检查前者触发 `lark_notify`、后者不触发。

**Acceptance Scenarios**:

1. **Given** 报告含提问，**When** 调度会话处理它，**Then** 用 `lark_notify` 转达提问并把任务设为 `waiting_user`。
2. **Given** 报告含结果、里程碑或阻塞，**When** 调度会话处理它，**Then** 用 `lark_notify` 转达。
3. **Given** 报告只是确认或复述本次工作，**When** 调度会话处理它，**Then** 不通知用户，任务状态照常更新。
4. **Given** 同一批输入含多个任务的报告，**When** 调度会话需要通知，**Then** 每个任务单独发一条 `lark_notify`，各自带该任务的 `task_id`；同一任务的内容合并为一条。
5. **Given** 用户发来任意一条消息，**When** 调度会话处理它，**Then** 回复该消息，包括「好的」「收到」这类简短消息。
6. **Given** 一批输入只含报告、失败通知、归档通知或日志注入消息，**When** 调度会话处理它们，**Then** 不为这些消息本身回复。

### User Story 4 - 用户的话不一定转发给任务会话 (Priority: P2)

用户对调度会话说「某任务在等一个值，暂时不用动」。调度会话判断这是给自己的说明，不是给任务会话的指令，因此不转发，只记录并回应用户。

**Why this priority**: 把这类说明转发给任务会话会让它开新一轮，产生无谓的工作与自动上报。

**Independent Test**: 发一条点名未结束任务、内容是「暂时不用动」的消息，检查调度会话没有调用 `session_send`，并用 `task_update` 记录后回应。

**Acceptance Scenarios**:

1. **Given** 用户消息点名某任务，内容是要求任务会话执行、补充或回答，**When** 调度会话处理它，**Then** 追加到任务并投递给任务会话。
2. **Given** 用户消息点名某任务，内容只是给调度会话的说明，**When** 调度会话处理它，**Then** 不投递给任务会话，用 `task_update` 把它记进该任务的消息列表，并回应用户。
3. **Given** 调度会话无法判断是否需要转发，**When** 处理该消息，**Then** 询问用户。

---

### User Story 5 - 调度会话自己读报告文件 (Priority: P2)

任务会话上报后，报告存成调度工作区里的文件。调度会话收到的注入块只给出报告标识与文件路径，它按需读取文件内容。

**Why this priority**: 报告正文直接进入调度会话上下文，会让长报告反复占用上下文、触发压缩；读文件让调度会话决定读多少、何时读。

**Independent Test**: 让被管理会话调用一次带长正文与附件的 `send_report`，检查调度工作区出现报告文件与附件副本，注入块含文件路径且不含正文。

**Acceptance Scenarios**:

1. **Given** 被管理会话调用 `send_report`，**When** 上报成功，**Then** 报告文件写入调度工作区，注入块只带标识与路径，不含正文。
2. **Given** 一轮自动上报，**When** 上报成功，**Then** 存档与注入方式和 `send_report` 相同。
3. **Given** 调度会话收到注入块，**When** 需要报告内容，**Then** 读取块中的报告文件与附件。
4. **Given** 任务已归档，**When** 调度会话按块中路径读取失败，**Then** 改读 `archive/<taskId>/reports/` 下的同名文件。
5. **Given** 存档后 git 提交失败，**When** 注入已完成，**Then** 行为与现状一致：上报仍算送达，工具结果附带 warning。

---

### User Story 6 - 长内容以可折叠卡片发给用户 (Priority: P2)

报告很长时，调度会话调用 `lark_notify` 的卡片模式。用户在飞书看到一张卡片：模型写的一句总结常显，例如「xxx 任务需要确认」「xxx 已完成」；完整 Markdown 默认收起，展开后可读。每个任务各发一张卡片。

**Why this priority**: 长报告以纯文本推送会刷屏并被拆成多条；卡片让用户先看摘要，需要时再展开。

**Independent Test**: 在调度会话以卡片模式调用 `lark_notify`，检查飞书收到一张卡片，完整内容默认收起，展开后 Markdown 完整。

**Acceptance Scenarios**:

1. **Given** 调度会话以卡片模式调用 `lark_notify`，**When** 发送成功，**Then** 用户收到一张卡片，常显一句总结，完整 Markdown 默认收起。
2. **Given** 调度会话以默认文本模式调用 `lark_notify`，**When** 发送，**Then** 行为与现状一致，只发纯文本。
3. **Given** 卡片模式带 `reply_to`，**When** 发送，**Then** 卡片引用该用户消息。
4. **Given** 卡片内容超过单张上限，**When** 发送，**Then** 按 Markdown 段落边界拆成多张卡片，每张带总结句与序号。
5. **Given** 任何会话，**When** 没有调用卡片模式，**Then** 插件不自动发卡片。
6. **Given** 调用带 `task_id`，**When** 发送成功，**Then** 通知标明该任务。
7. **Given** 调用成功，**When** 查看工具结果，**Then** 结果只含消息标识，不含分段数、回复目标或会话标识。

---

### User Story 7 - 调度会话知道用户直接与任务会话的交互 (Priority: P2)

任务会话上报了一个问题。用户没有回飞书，而是打开任务会话直接在 GUI 里回答。插件把这条消息记进任务日志。调度会话下一次运行时收到这条日志，知道用户已经回答，把任务改回 `in_progress`，不再追问用户。

**Why this priority**: 调度会话不知道用户已直接回答时，会让任务一直停在 `waiting_user`，并可能重复向用户提问。

**Independent Test**: 在被管理会话的 GUI 输入一条消息，检查 `task-logs/<taskId>.jsonl` 新增一条；随后触发调度会话一步，检查请求里出现该条目一次；再触发一步，检查不再重复出现。

**Acceptance Scenarios**:

1. **Given** 任务会话被管理，**When** 用户在它的 GUI 直接发消息，**Then** 日志新增一条用户直接消息条目，调度会话不被唤醒。
2. **Given** 用户在 GUI 主动停止任务会话的当前轮次，**When** 轮次以用户取消结束，**Then** 日志新增一条停止条目。
3. **Given** 任务结束触发会话归档并停止运行中的轮次，**When** 该轮次以取消结束，**Then** 不写日志，也不重建日志文件。
4. **Given** 日志有调度会话还没收到的条目，**When** 调度会话下一次 pre-step，**Then** 这些条目按时间升序合成一条消息，排在桥接提醒之后、本批第一条 `<lark-message>` 之前。
5. **Given** 条目已注入过，**When** 调度会话再次 pre-step 或被压缩后 pre-step，**Then** 不再注入该条目。
6. **Given** 调度会话是全新会话，**When** 它第一次 pre-step，**Then** 注入一条未结束任务快照，附各任务最新报告之后的日志条目；没有未结束任务时注入一条空快照。
7. **Given** 调度会话收到任务处于 `waiting_user` 时的用户直接消息条目，**When** 它处理，**Then** 用 `task_update` 设为 `in_progress`，不通知用户。
8. **Given** 任务结束，**When** 任务归档，**Then** 日志文件移到 `archive/<taskId>/task-log.jsonl` 并与归档一并提交。

### Edge Cases

- 报告到达时调度会话正在运行：报告并入当前轮次处理，回应规则不变。
- 报告在调度会话轮次刚结束时到达：兜底处理改为 followup，不应停留到下一条用户消息才被处理。
- 重发请求会让任务会话开新一轮。按 D-004，本次假设任务会话按请求调用 `send_report`，不设次数上限与兜底。
- `task_id` 指向不存在或已结束的任务：`lark_notify` 返回错误，不发送。
- 台账校验失败按空台账处理时，带 `task_id` 的调用报错、不发送。
- `lark-super-agent` 行停用或调度工作区未配置时，不带 `task_id` 的 `lark_notify` 照常发送。
- 报告文件被用户手动删除或移动：调度会话读取失败时如实告诉用户，并给出报告标识。
- 失败通知 `<task_session_failure>` 与归档通知 `<task_session_archived>` 的投递格式保持现状。
- 卡片模式发送失败：工具返回失败结果；调度会话按桥接提醒把完整内容留在正文，并改用文本模式或说明失败。
- 卡片或多段发送中第 n 条失败：错误说明已发送条数与第一条消息标识，调度会话只补发剩余部分。
- 卡片中的 Markdown 含飞书卡片不支持的语法：显示可能与网页不同，内容不丢失。
- 用户引用一张卡片回复：被引消息按现有引用读取流程呈现。
- 经调度会话 `session_send` 投递的消息来源是 `dsh-plugin-meta-tools`，不算用户直接消息，不入日志。
- 未被管理的会话收到用户消息时不写日志。
- 同一事件被观察两次时，条目 id 相同，日志与注入都不重复。
- 注入消息因请求失败没有写入会话日志时，下一次 pre-step 会再次注入。
- 原文超过 2000 字符时日志截断并注明；用户需要全文时调度会话可读任务会话。
- 同一任务的多条日志在同一步到达时，合在同一条注入消息里。
- 任务取消管理（`unmanaged`）、会话归档（`session_archived`）与会话缺失（`session_missing`）三种结束途径都按同一规则迁移日志。

## Requirements *(mandatory)*

### Functional Requirements

**回应时机**

- **FR-001**: 调度提示词 MUST 写明用户只能看到 `lark_notify` 的内容，调度会话的正文不会送达用户。
- **FR-002**: `session_create`、`session_send`、`session_manage`、`session_unmanage` 或 `task_end` 成功后，调度会话 MUST 在下一步调用 `lark_notify` 回应用户。置顶等收尾 MUST 与该通知同步执行或排在其后。
- **FR-003**: 收尾操作失败时，调度会话 MUST 另发一条简短 `lark_notify` 说明。`prompt.ts:60` 的「say so in the same reply」MUST 改为这一口径。
- **FR-004**: 调度会话 MUST 按任务分开通知：同一任务的内容合并为一条 `lark_notify` 并带该任务的 `task_id`，不同任务分开发送；与任务无关的内容单独一条。在通知之后到达的消息 MUST 单独回应。
- **FR-005**: 桥接提醒的「连续多条 `<lark-message>` 只回复一次」MUST 改为：同一批输入内同一任务的内容合并为一条回复，不同任务各回一条；通知之后到达的消息单独回复。
- **FR-006**: 调度会话转达与某个任务相关的内容时 SHOULD 用该任务最近一条用户消息作 `reply_to`；为此创建任务与追加消息时 MUST 传入用户消息的 `message_id`。

**报告分类与重发**

- **FR-007**: 调度提示词 MUST 说明报告有两类来源：`origin="turn_end"` 是轮次结束时自动取最后一段文本发出，`origin="send_report"` 是任务会话主动发出。
- **FR-008**: 报告既没有描述任务当前状态、也没有需要用户确认的点时，调度会话 MUST 向对应任务会话发一次重发请求，要求用 `send_report` 报告任务当前状态与需要用户确认的点。`turn_end` 与 `send_report` 两类报告都适用。本次不设次数上限与兜底。
- **FR-009**: 调度会话 MUST NOT 向任务会话发送对报告的确认、转述或自身回复。发往任务会话的消息 MUST 只有两类：用户本人的指令、补充或回答，以及 FR-008 的重发请求。
- **FR-010**: `prompt.ts:35` 的歧义表述 MUST 改为：用户回答任务提问时，追加回答并投递给任务会话。

**联系用户**

- **FR-011**: 调度会话 MUST 只在本份报告含新的结果、里程碑、阻塞、失败或提问时通知用户。报告只是确认或复述本次工作时 MUST NOT 通知。判定 MUST NOT 依赖「与上次通知重复」。
- **FR-012**: 无论是否通知，调度会话 MUST 按报告类型更新任务状态：`progress` 设为 `in_progress`，`question` 设为 `waiting_user`。
- **FR-013**: 任务会话每次轮次失败，调度会话 MUST 把任务设为 `failed` 并就该次失败通知用户一次；同一任务的多条失败通知不合并。用户要求后才重试。
- **FR-014**: 调度会话 MUST 回复用户发来的每一条消息。
- **FR-015**: 日志注入消息、上报块、失败通知与归档通知 MUST NOT 触发回复。
- **FR-016**: 一批输出含多个任务的内容时，通知方式 MUST 按 FR-004 处理，MUST NOT 因合并而丢失任一任务的内容。

**转发判断**

- **FR-017**: 调度会话 MUST 先判断点名任务的用户消息是否是给任务会话的指令，再决定是否转发。给调度会话自己的说明 MUST NOT 转发，MUST 用 `task_update` 的 `add_message` 记进该任务的消息列表后回应用户。
- **FR-018**: 无法判断是否转发时，调度会话 MUST 询问用户。

**报告存档与注入**

- **FR-019**: `send_report` 与自动上报 MUST 都把报告存成调度工作区的文件，附件同样复制到调度工作区；附件限 Markdown。现状已满足，本次保持。
- **FR-020**: 注入调度会话的上报块 MUST 保留 `sessionid`、`reportid`、`taskid`、`kind`、`origin` 属性，MUST 加报告文件路径与附件副本路径，MUST NOT 带 `desc` 与报告正文。
- **FR-021**: 块内路径 MUST 相对调度工作区根书写，以 `/` 分隔，报告位于 `reports/<taskId>/<reportId>.md`，附件副本位于同目录。
- **FR-022**: 调度提示词 MUST 要求调度会话处理报告时读取报告文件，需要时读取附件；任务归档后 MUST 改读 `archive/<taskId>/reports/`。
- **FR-023**: 调度提示词 MUST 说明 `desc` 只出现在报告文件的 front matter 中，需要修正任务标题或理解任务范围时读取该文件。
- **FR-024**: 上报投递 MUST 复用飞书消息注入的轮次结束兜底：投递后会话已空闲且消息仍在排队时改为 followup，使报告不停留到下一次唤醒。

**卡片通知**

- **FR-025**: `lark_notify` MUST 新增可选参数 `mode`，取 `text`（默认）或 `card`；`card` 模式用 `summary` 传一句总结、用 `text` 传完整 Markdown。未传 `mode` 时行为保持现状。
- **FR-026**: `card` 模式 MUST 让总结常显、完整 Markdown 默认收起。
- **FR-027**: `card` 模式 MUST 支持 `reply_to`。内容超过单张卡片上限（飞书卡片 JSON 30 KB）时 MUST 按 Markdown 段落边界拆成多张，每张带总结句与序号；整体失败时 MUST 返回错误，MUST NOT 自动回落为文本。
- **FR-028**: 多段或多张发送中部分成功后失败时，错误 MUST 说明已发送条数与第一条消息标识；调度提示词 MUST 要求只补发剩余部分或改发一条说明，不重发整批。
- **FR-029**: 插件 MUST NOT 自动发卡片；卡片只由调度会话主动调用。调度提示词 MUST 说明何时使用卡片，例如报告特别长时。
- **FR-030**: `lark_notify` MUST 新增可选 `task_id` 参数，文本模式与卡片模式都可使用。任务不存在或已结束时 MUST 返回错误、不发送。
- **FR-031**: 台账查找 MUST 由 `lark_notify` 自行读取调度工作区完成，MUST NOT 依赖 `lark-super-agent` 行是否启用。台账或调度工作区根不可读时，带 `task_id` 的调用 MUST 返回错误并不发送；不带 `task_id` 的调用 MUST 照常发送。
- **FR-032**: 带 `task_id` 时，任务名 MUST 由插件补写：飞书卡片标题与文本模式首行写「<title> (<task id>)」，正文 MUST NOT 重复该前缀。调度提示词与桥接提醒 MUST 说明带 `task_id` 的调用由插件补写任务名。
- **FR-033**: 按任务分开发送 MUST 同样适用于文本模式：同一任务的内容合并为一条，不同任务分开发送，与任务无关的内容单独一条。
- **FR-034**: 模型看到的 `lark_notify` 成功结果 MUST 只含第一条消息的标识；分段数、回复目标与会话标识 MUST 移除。失败结果 MUST 保持现有的错误码与说明。
- **FR-035**: 带 `task_id` 时，GUI 通知卡片的会话链接 MUST 指向该任务的会话。任务会话 id MUST 由执行体按 `task_id` 查出并放进结果值，只由 `presentationMeta` 投影给 GUI，模型可见的 `render` 文本 MUST NOT 含该 id。未带 `task_id` 时 MUST NOT 显示会话链接。任务会话已归档时沿用现有的「已归档」显示。
- **FR-036**: GUI 通知卡片的成功识别 MUST 同时支持 FR-034 的新结果文案与历史结果文案，使旧会话的卡片继续显示。
- **FR-037**: GUI 通知卡片 MUST 显示总结句与完整 Markdown 原文（`card` 模式），或正文（`text` 模式），带 `task_id` 时 MUST 显示该 task id 与任务会话链接。

**任务日志**

- **FR-038**: 被管理会话收到 `source.kind` 为 `user` 的消息时，插件 MUST 在调度工作区 `task-logs/<taskId>.jsonl` 追加一条用户直接消息条目。
- **FR-039**: 被管理会话的轮次以 `user` 取消结束、且该会话不在归档流程中时，插件 MUST 追加一条停止条目。由任务归档、插件停用或宿主关闭引发的取消 MUST NOT 记录。
- **FR-040**: 日志写入 MUST 在调度工作区的串行队列内完成，并在写入前确认该任务仍未结束；任务已结束时 MUST 丢弃该条目，MUST NOT 重建日志文件。
- **FR-041**: 任务会话的回复 MUST NOT 入日志。
- **FR-042**: 每条日志 MUST 含条目 id、时间、taskId、任务会话 id、事件类型与用户原文；条目 id MUST 由任务会话 id 与事件 seq 派生，同一事件重复观察 MUST 得到同一条目。原文超过 2000 字符时 MUST 截断并注明。
- **FR-043**: 写日志 MUST NOT 唤醒调度会话。
- **FR-044**: 调度会话每次 pre-step，插件 MUST 注入该会话事件日志中还没有的条目。注入消息 MUST 带来源标记与条目 id，判断已注入时 MUST 扫描完整事件日志，包括已压缩的部分；已注入判定 MUST 只依赖事件日志中的这些标记。
- **FR-045**: 调度会话第一次 pre-step 时 MUST 注入一条快照：全部未结束任务的标题、状态、工作区与最新报告路径（按 FR-021 的路径形态），附各任务在最新报告之后的日志条目；没有未结束任务时 MUST 注入一条空快照，使标记落地。
- **FR-046**: 同一步的条目 MUST 按时间升序合成一条消息，排在桥接提醒之后、本批第一条 `<lark-message>` 之前。
- **FR-047**: 调度提示词 MUST 规定：收到日志条目不通知用户；任务处于 `waiting_user` 时收到用户直接消息条目，用 `task_update` 设为 `in_progress`；停止条目只告知用户停止过，不改变任务状态。
- **FR-048**: 任务结束时，日志文件 MUST 移到 `archive/<taskId>/task-log.jsonl`，归档提交 MUST 包含归档下的新文件；源文件已被 git 跟踪时 MUST 同时包含其删除。日志平时不提交，源文件通常未被跟踪，没有可提交的删除。单条写入 MUST NOT 单独提交。
- **FR-049**: 日志 MUST 与报告存档、台账互不写入对方：台账 `task.messages` 记调度会话处理过的用户消息，包括已投递的消息与仅记入台账的说明性消息；报告存档只记上报。

**文档与测试**

- **FR-050**: `README.md` MUST 说明 `lark_notify` 的卡片模式与调度会话的回应规则。
- **FR-051**: `docs/how-it-works.md` 与 `docs/known-risks.md` MUST 更新上报注入、卡片通知、任务日志与飞书消息立即注入的描述，删除 15 秒批量注入的过时内容，并在调度工作区目录表中加入 `task-logs/<taskId>.jsonl` 与归档位置。

### Key Entities

- **报告**：任务会话的一次上报，来源为 `turn_end` 或 `send_report`，类型为 `progress` 或 `question`，存为调度工作区 `reports/<taskId>/<reportId>.md`，归档后位于 `archive/<taskId>/reports/`。
- **上报块**：注入调度会话的 `<task_session_message>`，携带报告标识与工作区相对路径，不含正文。
- **重发请求**：调度会话发给任务会话的一条消息，要求用 `send_report` 报告当前状态与待确认点。
- **通知**：`lark_notify` 的一次调用，可关联一个任务。`text` 模式发送正文；`card` 模式常显一句总结，完整 Markdown 默认收起。
- **任务日志**：调度工作区 `task-logs/<taskId>.jsonl`，记录调度会话看不到的用户直接交互，任务结束时移到 `archive/<taskId>/task-log.jsonl`。
- **日志注入消息**：pre-step 插入调度会话的一条消息，带来源标记与条目 id；全新会话的首条为任务快照，可能为空快照。
- **任务**：`message-task-status.json` 中的未结束任务，状态取 `in_progress`、`waiting_user` 或 `failed`。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在派发、补充、取消三类场景的实机验收中，每次成功的下发调用之后，下一步都含 `lark_notify`。
- **SC-002**: 在充分报告的验收场景中，调度会话向任务会话发送的消息数为 0。
- **SC-003**: 在不充分报告的验收场景中，调度会话向任务会话发出重发请求，任务会话随后用 `send_report` 报告当前状态。
- **SC-004**: 在只含确认或复述内容的报告场景中，用户收到的飞书消息数为 0。
- **SC-005**: 「暂时不用动」类消息的验收场景中，`session_send` 调用数为 0。
- **SC-006**: 单元测试断言：注入调度会话的上报块不含报告正文，含按工作区相对路径可读取的报告文件路径。
- **SC-007**: 轮次刚结束时投递的报告，在不发新用户消息的情况下被调度会话处理。
- **SC-008**: 卡片模式发出的飞书消息是一张卡片，完整内容默认收起；文本模式的发送命令与现状一致。
- **SC-009**: 一批输入含两个任务的报告时，用户收到两条通知，每条只含一个任务的内容。
- **SC-010**: 实机验收中，用户发来的每条消息都得到回复；只含报告与通知的一批输入不多出回复。
- **SC-011**: 单元测试断言：成功结果只含第一条消息的标识；带 `task_id` 的发送消息含「<title> (<task id>)」前缀且正文不重复；新旧结果文案都生成 GUI 卡片。
- **SC-012**: 单元测试断言：用户直接消息写入日志一次，同一事件重复观察不重复写入；同一条目在同一调度会话中只注入一次，压缩后也不重复；全新会话首次 pre-step 注入快照，无任务时注入空快照。
- **SC-013**: 单元测试断言：任务归档时日志移入 `archive/<taskId>/task-log.jsonl`，归档提交含归档下的新文件，源文件被跟踪时同时含其删除，且归档后工作区保持干净；归档触发的取消不写日志。
- **SC-014**: 实机验收中，用户在任务会话 GUI 直接回答提问后，调度会话下一次运行时把任务改为 `in_progress` 且不通知用户。

## Assumptions

- 调度会话、任务会话、`send_report`、自动上报、失败通知与归档通知的其余行为保持现状。
- 报告充分与否由调度会话按提示词判断，插件不在代码中判定。
- 卡片使用 `lark-cli im +messages-send` 与 `+messages-reply` 的 interactive 消息发送，沿用现有 bot 身份与 `im:message:send_as_bot` 权限。
- 卡片不含交互按钮，不需要订阅卡片回调事件。
- 桥接提醒对所有桥接会话生效；调度会话专属的回应规则写在调度提示词中，桥接提醒只保留通用规则。
- 任务日志在归档后只作历史留存，插件与调度会话都不再读取。
