## 现状基线

1. `lark_notify` 没有专用展示：成功时宿主默认工具行只显示「已发送给用户（N 条）」或「已回复给用户（N 条）」，发给用户的正文不在对话里呈现。
2. `send_report` 成功时在轮次层级产出专用卡片，展示类型、任务简介、Markdown 正文与附件；进行中、失败与中断沿用宿主默认工具行。
3. 上报卡片容器文字使用次要前景色 `--dsw-alias-label-secondary`，与对话正文的主前景色不同。
4. `lark_notify` 参数为必填 `text` 与可选 `reply_to`；结果含 `ok`、分段数、首条 `messageId` 与 `replyTo`。
5. `SA-调度会话` 提示词按在场状态选择渠道：在电脑旁时在正文回复，离开时经 `lark_notify`。
6. 桥接提醒规定飞书消息经 `lark_notify` 回复，其他来源的消息按普通方式回复。
7. 在场提醒只注入调度会话；被管理会话的提问拦截由服务按在场状态执行。以上在场机制本期保留。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - lark_notify 全文以通知卡片呈现 (Priority: P1)

用户在 GUI 查看桥接会话。`lark_notify` 成功后，对话中出现通知卡片，用户不展开工具行就能读到这次发给用户的完整内容与投递回执。

**Why this priority**: 当前对话里只有「已发送给用户（N 条）」一行，发给用户的内容在会话内不可见。这是需求的核心缺口。

**Independent Test**: 在桥接会话里调用一次 `lark_notify` 发送带换行的较长文本，在 GUI 中查看该轮。

**Acceptance Scenarios**:

1. **Given** 一次成功的 `lark_notify`，**When** 用户查看该轮，**Then** 通知卡片显示完整正文，换行保留，Markdown 记号按原文显示。
2. **Given** 一次成功的 `lark_notify`，**When** 用户查看卡片，**Then** 卡片显示发送或回复、分段数，`messageId` 存在时一并显示。
3. **Given** 该轮过程分组已折叠，**When** 用户查看，**Then** 通知卡片默认可见。
4. **Given** 一次带 `reply_to` 的成功调用，**When** 用户查看，**Then** 卡片表明这是一次回复。
5. **Given** 历史轮次只加载到成功结果，**When** 用户查看，**Then** 同样显示通知卡片。

---

### User Story 2 - 上报卡片正文与对话正文同色 (Priority: P1)

用户查看 `send_report` 上报卡片时，正文、任务简介与附件名使用与宿主对话正文相同的前景色，不再呈现为次要灰色。通知卡片也遵循同一颜色规则。

**Why this priority**: 上报与通知承载给用户的主要内容，颜色弱于正文会让用户误以为它们是辅助信息。用户明确要求上报 UI 与正文一样是黑色。

**Independent Test**: 在 GUI 并排查看一条普通助手正文与一张上报卡片，对比内容文字颜色。

**Acceptance Scenarios**:

1. **Given** 一张含正文、任务简介与附件的上报卡片，**When** 用户查看，**Then** 这些内容文字与宿主对话正文使用相同前景色。
2. **Given** 一张通知卡片，**When** 用户查看，**Then** 通知正文与宿主对话正文使用相同前景色。
3. **Given** 宿主切换明暗主题，**When** 用户查看两类卡片，**Then** 内容文字继续跟随宿主正文前景令牌。

---

### User Story 3 - 桥接与调度会话始终经 lark_notify 通信 (Priority: P2)

桥接会话与调度会话面向用户的完整回复都通过 `lark_notify` 送达，不随消息来源或在场状态切换渠道。送达后正文最多一句话概述。用户在飞书读完整内容，在 GUI 通过通知卡片读同一内容。

**Why this priority**: 统一通知方式后，用户在电脑旁也能从卡片读到内容，不必依赖正文渠道；正文只保留一句概述，避免同一内容出现两份。

**Independent Test**: 审查调度提示词与桥接提醒全文；在真实宿主「在电脑旁」状态下从 GUI 给调度会话发一条消息，观察是否仍经 `lark_notify` 送达且正文只剩一句概述。

**Acceptance Scenarios**:

1. **Given** `SA-调度会话` 提示词，**When** 审查全文，**Then** 规定回复与转达一律经 `lark_notify`，不再按在场状态选择渠道。
2. **Given** 调度提示词，**When** 审查全文，**Then** 规定 `lark_notify` 送达后正文最多一句话概述，允许为空。
3. **Given** 桥接提醒，**When** 审查全文，**Then** 规定桥接会话的所有用户消息都经 `lark_notify` 回复，正文最多一句话概述。
4. **Given** 用户在场状态为「在电脑旁」，**When** 调度会话回复 GUI 消息，**Then** 完整内容经 `lark_notify` 送达，正文只有一句话概述。
5. **Given** 一条任务上报需要转达，**When** 调度会话转达，**Then** 转达内容经 `lark_notify` 原文送达，正文不复述。

---

### User Story 4 - 未送达的调用保持默认展示 (Priority: P3)

进行中、失败与中断的 `lark_notify` 沿用宿主默认工具行并显示错误，不出现通知卡片。用户能区分内容已送达与未送达。

**Why this priority**: 卡片是送达凭证，其他状态必须沿用现状。

**Independent Test**: 分别触发一次失败与一次成功的 `lark_notify`，对比展示形态。

**Acceptance Scenarios**:

1. **Given** `lark_notify` 正在执行，**When** 用户查看，**Then** 显示宿主默认工具行，无卡片。
2. **Given** `lark_notify` 返回失败结果，**When** 用户查看，**Then** 显示宿主默认工具行与错误信息，无卡片。
3. **Given** `lark_notify` 被中断，**When** 用户查看，**Then** 显示宿主默认中断样式，无卡片。

---

### Edge Cases

- 长文本被拆成多段发送：卡片仍对应一次调用，显示全文与分段数。
- 同一轮多次调用 `lark_notify`：每次成功都出一张卡片。
- 调用事件不在已加载历史窗口内：成功结果独立产出卡片，沿用 `send_report` 卡片策略。
- 停用 `lark-super-agent` 行时，普通桥接会话的 `lark_notify` 仍显示卡片；提示词规则只影响使用对应预设或桥接提醒的会话。
- 上报卡片只有附件、正文为空时，附件名仍使用正文前景色。
- `lark_notify` 送达失败时，模型可在正文补充面向用户的内容；一句概述的约束以成功送达为前提。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 一次成功的 `lark_notify` MUST 在对话中显示专用通知卡片，包含发给用户的完整正文；正文按纯文本保留换行，不作 Markdown 渲染。
- **FR-002**: 通知卡片 MUST 显示发送或回复与分段数；`messageId` 可用时 MUST 显示。
- **FR-003**: 通知卡片 MUST 与 `send_report` 卡片同级：位于轮次层级，不进入过程分组，轮次折叠后默认可见。
- **FR-004**: 进行中、失败与中断的 `lark_notify` MUST 沿用宿主默认工具行，不显示卡片。
- **FR-005**: 历史消息加载出成功的 `lark_notify` 结果时 MUST 显示通知卡片。
- **FR-006**: 通知卡片的界面文案 MUST 提供中英词典条目并按现有回退规则工作。
- **FR-007**: `send_report` 卡片的正文、任务简介与附件名 MUST 使用宿主对话正文的主前景色；卡片容器 MUST 向 Markdown 正文提供同一前景色，不再以次要前景色作为内容默认色。
- **FR-008**: 通知卡片的正文 MUST 使用与 FR-007 相同的主前景色。
- **FR-009**: `SA-调度会话` 提示词 MUST 规定面向用户的回复与转达一律经 `lark_notify`，不随在场状态选择渠道。
- **FR-010**: `SA-调度会话` 提示词 MUST 规定 `lark_notify` 成功送达后正文最多一句话概述，允许为空；完整内容只写在通知里。
- **FR-011**: 调度提示词的在场渠道段落 MUST 删除；调度会话 MUST 停止注入在场提醒。
- **FR-012**: 桥接提醒 MUST 改为桥接会话的所有用户消息都经 `lark_notify` 回复，正文最多一句话概述；连续多条飞书消息仍合并为一次通知。
- **FR-013**: `lark_notify` 的参数、校验、分段、发送行为与返回结构 MUST 保持现状。
- **FR-014**: `send_report` 的参数、投递行为、卡片结构与 Markdown 渲染方式 MUST 保持现状；本次只改颜色。
- **FR-015**: 全局在场状态、页脚按钮、自动更新开关、闹钟、节假日数据与被管理会话的提问拦截 MUST 保持现状。
- **FR-016**: 用户可见行为变化 MUST 同步 `README.md`、`docs/how-it-works.md` 与变更日志。

### Key Entities

- **通知卡片**: 一次成功 `lark_notify` 的对话内展示，承载完整正文与投递回执。
- **投递回执**: 发送或回复、分段数与可选消息 id。
- **上报卡片**: 一次成功 `send_report` 的既有展示；本次只调整内容文字颜色。
- **正文概述**: `lark_notify` 送达后正文中最多一句的简短说明，允许为空。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 实机触发一次成功的 `lark_notify`，截图显示完整正文、回执与分段数，轮次结束后无需点击即可见；失败与进行中沿用默认工具行。
- **SC-002**: 实机截图中，`send_report` 卡片正文、任务简介、附件名与 `lark_notify` 卡片正文的颜色和宿主对话正文一致。
- **SC-003**: 调度提示词与桥接提醒全文审查通过：含统一渠道与一句概述规则，无相互矛盾的渠道表述。
- **SC-004**: 真实宿主「在电脑旁」状态下从 GUI 发一条消息给调度会话，用户经飞书收到完整回复，会话正文不超过一句话概述。
- **SC-005**: `pnpm full-check` 全部通过；除颜色断言外，`send_report` 既有行为用例零修改通过。

## Assumptions

- 卡片注册与展示形态参照 `send_report` 卡片的既有模式；`lark_notify` 卡片不复用 Markdown 渲染，以避免与飞书纯文本观感不一致。
- 「和正文一样是黑色」指使用宿主正文前景令牌，随明暗主题变化，不写死颜色值。
- 上报卡片的回执、类型标签与附件完整路径等辅助信息保留现有视觉层级；用户要求的主要内容文字统一为正文色。
- 本期保留最初需求中的调度提示词与桥接提醒渠道统一；取消的是在场机制移除及其连带清理。
- 调度会话停止注入在场提醒后，全局在场状态仍用于被管理会话的提问拦截，其余在场功能不受影响。
- 验证沿用 `real-device-test` 技能，覆盖两类卡片渲染、颜色与统一渠道规则。
