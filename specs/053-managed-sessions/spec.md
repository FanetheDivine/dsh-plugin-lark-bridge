# Feature Specification: 调度会话统一管理任务会话

**Feature Branch**: `feat/053-managed-sessions`

**Created**: 2026-11-25

**Status**: Approved

**Input**: User description: "调整插件功能 让调度会话统一管理其他会话。1. 删除SA-工作会话 现在任何会话都可以被管理 这个preset里关于如何通过send_report响应用户的部分记作“S” S要着重强调completed和abandoned的重要性 要求谨慎选用 尤其是对于查询类的任务 用户可能有进一步的指示。2. 为所有非SA-工作会话注入send_report 但是desc里说明不得擅自调用 仅在用户要求时调用。没有被管理的会话调用这个报错。3. 用户离席时 对于被管理的会话 正在被提问的立刻中断并返回错误 后续的提问返回同样的错误 然后注入S。注意send_report的调用不是第一优先级的 让模型先提问 失败后再send_report 4. send_report的内容用一种特殊的ui展示出来 避免同时输出text和report的问题。（要求模型少输出text多输出报告）。send_report加一个参数 desc 要简单介绍自己的任务 但不强制添加。因为被管理的会话只直到用户第一句说了什么 不知道后续全景 允许模型调整。5. 对于被管理&turn结束&没有subagent正在进行&最新turn没有汇报过的会话 将会话输出的最后一段文本作为report内容发给调度会话 6. 关于“管理”也就是 用户希望借助调度会话统一控制的会话。只是一种会话状态 不再需要特定的preset 只记录到json里。7. 调度会话创建的新会话自动被管理。现在插件创建会话没有特殊性了 8. 让用户可以手动管理会话 暂时采用调度会话加tool通过sessionid进行管理。以及调度会话的提示词要改下 用户询问workspace/session等dsh元信息时 由调度会话自身回答。9. 措辞中 所有的“工作”替换为任务 包括英文 xml-tag 10. 忽略权限升级等其他需要用户参与的弹窗。核心思想：1. 用户可以自由控制哪些会话被管理 2. 被管理的会话 始终可以用调度会话进行管理并与用户交互 3.尽量不干扰原有流程的执行 让任务会话无感知"

- [D-020] Q: 不知情的会话不上报结束时任务如何结束 -> A: 除 `completed`/`abandoned` 上报外，用户要求结束时任务结束；用户在界面归档会话后任务结束。
- [D-024] Q: 取消管理或会话被归档后任务如何同步 -> A: 管理即任务，取消管理与会话归档都等于任务归档。可以分为两种结束状态记录；任务结束后不再复用。
- [D-026] Q: 用户在网页直接与被管理会话对话时自动上报如何处理 -> A: 照常转达。调度会话只按在场状态决定转达渠道，网页输入不影响。
- [D-021] Q: `send_report` 描述与 S 的冲突如何统一 -> A: 描述写明两个例外：收到要求改用 `send_report` 的系统提醒后可自主调用；`<dispatch_session_message>` 转来的请求视同用户要求。S 写明它覆盖描述中的限制。
- [D-022] Q: 调度会话如何区分自动上报 -> A: 自动上报带专门标记，表示会话已停下；调度会话按内容判断转达进度、转达提问并设为 `waiting_user`，或请用户确认完成。
- [D-023] Q: 是否调整自动上报的抑制条件 -> A: 保持「本轮上报过就不自动上报」。
- [D-028] Q: 不在已登记工作区的会话能否管理 -> A: 能。任务的工作区取该会话所在工作区，不受派发白名单限制。
- [D-029] Q: 任务由谁建立 -> A: `session_create` 新建会话时同时建立其任务，首条提示记为任务首条消息；手动管理工具为已有会话建立任务；删除 `task_create`；`task_update` 只改状态、标题与追加消息。
- [D-030] Q: 结束方式如何记录、是否归档会话 -> A: 任务都移入归档并记录结束原因。`completed`/`abandoned` 上报或用户要求结束时归档会话；取消管理时保持会话未归档；会话被归档时任务随之归档。本条细化 D-010。
- [D-031] Q: 「复用已有会话」与 `task_candidates` 是否保留 -> A: 删除。用户要复用已有会话时用手动管理工具管理它。
- [D-032] Q: `send_report` 的上报类型 -> A: 只保留 `progress` 与 `question`；删除 `completed` 与 `abandoned`。
- [D-033] Q: 任务何时结束 -> A: 调度会话自行判断任务是否完成。判断完成时先询问用户，用户确认后结束任务。用户要求结束或取消时立即结束。
- [D-034] Q: 任务结束是否归档会话 -> A: 任务归档不归档会话。用户要求归档会话时由调度会话单独调用会话归档工具。
- [D-035] Q: S 的语气与有效期 -> A: S 是一条临时指令，说明本次无法提问、改为用 `send_report` 提问，并要求后续忽略它。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用户离开时被管理会话经调度会话联系用户 (Priority: P1)

用户离开电脑。一个被管理会话在执行中需要用户决定，调用 `ask_user_question`。提问立即失败，会话随后收到 S，改用 `send_report` 的 `question` 上报。调度会话经飞书把问题转给用户，再把回答送回该会话。

**Why this priority**: 这是「被管理会话始终能与用户交互」的核心路径。

**Independent Test**: 把一个会话设为被管理，切换为离开，在该会话触发提问，确认提问报错、下一次请求含 S、`question` 上报送达调度会话。

**Acceptance Scenarios**:

1. **Given** 被管理会话正在等待 `ask_user_question` 的回答，**When** 在场状态切为离开，**Then** 该提问立即结束并返回离开错误。
2. **Given** 在场状态为离开，**When** 被管理会话再次调用 `ask_user_question`，**Then** 返回同一错误。
3. **Given** 被管理会话的提问因离开失败，**When** 下一次模型请求发出，**Then** 请求含一条内容为 S 的提醒；同一离开期间不重复插入。
4. **Given** 在场状态为离开，**When** 未被管理的会话调用 `ask_user_question`，**Then** 行为与宿主原生一致。
5. **Given** 会话收到 S，**When** 它以 `question` 调用 `send_report`，**Then** 调度会话收到带会话与任务标识的上报。
6. **Given** 已收到 S 的会话，用户回到电脑旁，**When** 会话再次需要用户决定，**Then** 它先调用 `ask_user_question`，提问照常显示。

### User Story 2 - 轮次结束自动上报 (Priority: P1)

被管理会话正常结束一轮，期间没有调用 `send_report`，也没有子代理在运行。插件把该轮最后一段文本作为 `progress` 上报发给调度会话。会话本身不需要知道调度会话的存在。

**Why this priority**: 它让未经提示的会话也能被统一跟踪，是「任务会话无感知」的基础。

**Independent Test**: 在被管理会话发一条消息，等待轮次结束，确认调度会话收到内容为最后一段文本的 `progress` 上报。

**Acceptance Scenarios**:

1. **Given** 被管理会话本轮没有上报且没有运行中的子代理，**When** 轮次正常结束，**Then** 调度会话收到一条 `progress` 上报，正文为最后一段文本。
2. **Given** 被管理会话本轮已调用 `send_report`，**When** 轮次结束，**Then** 不再自动上报。
3. **Given** 被管理会话仍有子代理运行，**When** 主轮次结束，**Then** 本轮不自动上报。
4. **Given** 轮次以错误结束，**When** 轮次结束，**Then** 只发送失败通知。
5. **Given** 轮次被取消，**When** 轮次结束，**Then** 不上报也不通知。
6. **Given** 会话未被管理，**When** 轮次结束，**Then** 不上报。

---

### User Story 3 - 用户自由选择被管理的会话 (Priority: P1)

用户在调度会话中给出会话 id，要求管理或取消管理该会话。管理一个会话就是为它建立任务，取消管理就是结束该任务。调度会话新建的会话自动被管理。

**Why this priority**: 管理范围由用户控制，取代原来的专用预设。

**Independent Test**: 在调度会话中管理一个普通会话，确认出现对应任务、该会话可成功调用 `send_report`；取消管理后任务归档，调用 `send_report` 报错。

**Acceptance Scenarios**:

1. **Given** 一个任意预设的普通会话，**When** 用户要求调度会话管理它，**Then** 出现一个对应该会话的未结束任务。
2. **Given** 调度会话用 `session_create` 新建会话，**When** 创建成功，**Then** 该会话自动被管理，预设取「任务会话预设」。
3. **Given** 一个被管理会话，**When** 用户要求取消管理，**Then** 其任务归档，之后的提问与上报按未被管理处理。
4. **Given** 会话 id 不存在、是调度会话自身或已被管理，**When** 调度会话尝试管理，**Then** 工具返回错误且记录不变。
5. **Given** 一个被管理会话，**When** 用户在界面归档它，**Then** 其任务归档。
6. **Given** 一个被管理会话，**When** 用户要求结束该任务，**Then** 任务归档。

---

### User Story 4 - 上报以专用界面展示 (Priority: P2)

被管理会话调用 `send_report` 后，会话界面以专用卡片展示上报的类型、任务简介、正文与附件。模型不必在正文重复上报内容。

**Why this priority**: 避免正文与上报重复输出，减少用户阅读负担。

**Independent Test**: 在 Web GUI 打开调用过 `send_report` 的会话，确认上报以卡片显示，字段完整。

**Acceptance Scenarios**:

1. **Given** 一次带 `desc` 的上报，**When** 用户查看会话，**Then** 卡片显示类型、`desc`、正文与附件列表。
2. **Given** 一次不带 `desc` 的上报，**When** 用户查看会话，**Then** 卡片省略简介，其余字段照常显示。

---

### User Story 5 - 调度会话直接回答 DSH 元信息 (Priority: P2)

用户在调度会话询问有哪些工作区、有哪些会话、某会话状态等 DSH 元信息。调度会话自行查询并回答，不建任务。

**Why this priority**: 元信息查询无需派发，派发只增加延迟。

**Independent Test**: 在调度会话问「现在有哪些会话」，确认直接回答且任务记录不变。

**Acceptance Scenarios**:

1. **Given** 用户询问工作区或会话信息，**When** 调度会话处理该消息，**Then** 调度会话直接回答，不建立任务。

---

### User Story 6 - 未被管理的会话保持原样 (Priority: P2)

用户日常使用的普通会话未被管理时，行为与宿主原生一致。`send_report` 虽然可见，但描述要求仅在用户要求时调用；调用时报错。

**Why this priority**: 「尽量不干扰原有流程」。

**Independent Test**: 在未被管理的会话中调用 `send_report`，确认返回未被管理的错误，调度会话无消息。

**Acceptance Scenarios**:

1. **Given** 未被管理的会话，**When** 调用 `send_report`，**Then** 返回错误，不存档也不投递。

### Edge Cases

- 上报时调度会话不可用：`send_report` 返回错误；自动上报只写日志。
- 同一轮里模型多次调用 `send_report`：每次都投递，本轮不再自动上报。
- 插件加载前就已开始等待的提问同样立即结束并返回离开错误。宿主不支持该中断方式时保持等待。
- 离开期间被中断的提问，用户回来后会话再次需要用户时仍先调用 `ask_user_question`。
- 权限升级等其他需要用户参与的弹窗在离开期间保持等待，插件不处理。

## Requirements *(mandatory)*

### Functional Requirements

#### 预设与管理状态

- **FR-001**: 插件 MUST 删除 `SA-工作会话` 预设，只保留 `SA-调度会话`。
- **FR-002**: 「被管理」MUST 与会话预设无关。管理即任务：一个被管理会话对应一个未结束任务，记录在调度工作区的 `message-task-status.json`。
- **FR-003**: 调度会话 MUST 提供按会话 id 管理与取消管理会话的工具。
- **FR-003a**: 手动管理 MUST 为该会话建立任务，任务的工作区取会话所在工作区，不受派发白名单限制。
- **FR-004**: 一个会话 MUST 最多对应一个未结束任务，一个任务 MUST 只对应一个会话。
- **FR-005**: 调度会话 MUST 不能管理自身。
- **FR-006**: 调度会话经 `session_create` 新建会话时 MUST 同时建立该会话的任务，首条提示记为任务首条消息。
- **FR-006a**: 插件 MUST 删除 `task_create`；`task_update` 只修改状态、标题与追加消息。
- **FR-007**: `session_create` MUST 去掉 `agent_preset` 参数，始终使用「任务会话预设」；该项为空时用宿主默认预设。
- **FR-008**: 「飞书任务与调度会话」配置页 MUST 在「任务会话模型」下方提供「任务会话预设」选择器，交互与主行「预设」一致，默认空值。
- **FR-009**: 以下任一情况 MUST 结束任务、移入归档并记录结束原因：用户确认任务完成、用户要求结束或取消、取消管理、会话被归档。
- **FR-009a**: 结束任务 MUST NOT 归档会话。用户要求归档会话时，由调度会话单独调用会话归档。
- **FR-009c**: 上报 MUST NOT 结束任务。
- **FR-009b**: 读取任务时 MUST 剔除会话已不存在的任务。

#### send_report

- **FR-010**: 除 `SA-调度会话` 外的会话 MUST 都能看到 `send_report`。
- **FR-011**: `send_report` 的描述 MUST 要求模型不得擅自调用，仅在用户要求时调用。例外有两个：收到要求改用 `send_report` 的系统提醒后可自主调用；`<dispatch_session_message>` 转来的请求视同用户要求。
- **FR-012**: 未被管理的会话调用 `send_report` MUST 返回错误，不存档、不投递。
- **FR-013**: `send_report` MUST 增加可选参数 `desc`，用于简要介绍调用方的任务，并随上报送达调度会话。
- **FR-014**: 任务会话中 `send_report` 的调用 MUST 以专用卡片展示类型、`desc`、正文与附件。

#### 离开时的提问

- **FR-015**: 在场状态切为离开时，被管理会话中正在等待的 `ask_user_question` MUST 立即结束并返回错误。
- **FR-016**: 离开期间被管理会话的后续 `ask_user_question` MUST 返回同一错误。
- **FR-017**: 被管理会话的提问因离开首次失败后，插件 MUST 在下一次模型请求前插入内容为 S 的 `<system-reminder>`；同一离开期间只插一次，压缩移除后补回。
- **FR-018**: 插件 MUST 只拦截 `ask_user_question`，权限升级等其他弹窗保持宿主原有行为。
- **FR-019**: 未被管理的会话与在电脑旁时的提问 MUST 保持宿主原有行为。

#### S 的内容

- **FR-020**: S MUST 要求模型需要用户时始终先调用 `ask_user_question`，当作用户在电脑旁；提问因用户离开而失败时，改用 `send_report` 与用户交互。
- **FR-020a**: 用户回到电脑旁时，插件 MUST 不插入恢复提醒。
- **FR-021**: S MUST 标明它是临时指令，要求后续忽略。
- **FR-022**: S MUST 说明此时用户无法回答问题，改用 `send_report` 的 `question` 提问。
- **FR-023**: S MUST 要求模型少写正文，把面向用户的内容放进上报，避免正文与上报重复。
- **FR-024**: S MUST 说明 `desc` 的用途：模型可按当前掌握的全貌简介或修正任务。
- **FR-024a**: S MUST 写明它覆盖 `send_report` 描述中「仅在用户要求时调用」的限制。

#### 被管理会话的其他行为

- **FR-025**: 被管理会话 MUST 保留 `<dispatch_session_message>` 来源包装与轮次失败通知。
- **FR-026**: 被管理会话 MUST 不插入在场提醒。

#### 自动上报

- **FR-027**: 被管理会话的轮次正常结束、没有运行中的子代理、且该轮没有调用 `send_report` 时，插件 MUST 把该轮最后一段文本作为 `progress` 上报投递给调度会话。
- **FR-028**: 自动上报 MUST 在两种在场状态下都生效。
- **FR-029**: 以错误或取消结束的轮次 MUST 不自动上报。
- **FR-029a**: 自动上报 MUST 带有区别于手动上报的标记，表示会话已停下。

#### 调度会话

- **FR-030**: 调度会话提示词 MUST 规定：用户询问工作区、会话等 DSH 元信息时由调度会话自行回答，不建任务。
- **FR-031**: 调度会话提示词 MUST 说明管理与取消管理工具的用法，并按 `desc` 修正任务标题与描述。
- **FR-031a**: 调度会话提示词 MUST 说明自动上报的处理：按内容转达进度，或转达提问并设为 `waiting_user`，或请用户确认完成。
- **FR-031b**: 调度会话提示词 MUST 规定由调度会话判断任务是否完成：判断完成时先询问用户，用户确认后才结束任务。
- **FR-031d**: 调度会话提示词 MUST 规定用户要求结束或取消任务时立即结束任务，并把请求转给会话。
- **FR-031e**: 调度会话提示词 MUST 规定上报类型只用于判断任务状态，`progress` 保持进行中，`question` 转为等待用户。
- **FR-031c**: 插件 MUST 删除 `task_candidates`；调度会话提示词 MUST 删除「复用已有会话」规则，用户要复用时改用手动管理。
- **FR-032**: 调度会话 MUST 能向任一被管理会话发送消息并接收其上报。

#### 措辞

- **FR-033**: 文案、提示词、工具描述、XML 标签与配置键中的「工作」MUST 改为「任务」，英文 `work`/`worker` 改为 `task`。「工作区」与 `workspace` 保持不变。
- **FR-034**: 旧配置键 MUST 不迁移、不兼容读取。

### Key Entities

- **被管理会话**: 用户希望经调度会话统一控制的会话。它与一个未结束任务一一对应，不单独记录。
- **S**: 用户离开时提问失败后插入的临时指令，按 FR-020 至 FR-024a、FR-035 重写。
- **上报**: `send_report` 或自动上报产生的记录，含类型、可选 `desc`、正文与附件。
- **任务**: 调度会话维护的任务记录，对应一个会话，记录在 `message-task-status.json`；结束后移入归档。
- **任务会话预设**: `session_create` 新建会话时使用的预设，空值跟随宿主默认。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 离开状态下，被管理会话的提问在切换后 1 秒内失败，下一次模型请求含 S。
- **SC-002**: 被管理会话每个正常结束、未上报、无运行中子代理的轮次恰好产生一次自动上报。
- **SC-003**: 未被管理会话的提问、轮次结束与工具调用均不产生上报或调度消息。
- **SC-004**: 用户只用会话 id 即可在调度会话中完成管理与取消管理。
- **SC-005**: 代码、提示词、文档与界面文案中不再出现表示会话角色的「工作会话」「worker」。
- **SC-006**: 现有测试与新增测试全部通过，`pnpm check` 无新增问题。

## Assumptions

- 调度会话即 `state.json` 记录的桥接会话。
- 离开错误的正文说明用户不在电脑旁。
- 失败通知继续只发给调度会话，不进入上报存档。
- `lark_notify` 仍只在桥接会话可用。
- 不处理过往数据：旧 `SA-工作会话` 会话、旧任务与旧配置键均保持原状。

### 探索结论

- 宿主工具注册支持按会话判定可见性，`send_report` 可对调度会话隐藏。
- 插件可以给 `ask_user_question` 的执行换上自己的中止信号，离开时中止即返回错误。
- 宿主网关保存全部等待中的提问请求。插件可以按会话结束这些请求，并让提问返回插件给定的错误文本；轮次不中止，提问卡片随之关闭。插件加载前已开始的提问也能这样中断。该能力属于宿主内部实现，宿主升级后可能失效。
- 插件可以在执行前直接拒绝 `ask_user_question`，权限审批走独立的审批机制，不受影响。
- 会话事件流提供轮次结束、工具调用与助手消息，可判断本轮是否上报并取得最后一段文本。
- 宿主可查询会话的运行中子代理，并提供会话归档事件。
- Web 客户端可按工具名为 `send_report` 注册专用卡片。
