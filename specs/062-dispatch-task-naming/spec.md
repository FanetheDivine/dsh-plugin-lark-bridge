## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新建任务后的通知带上名称与 id (Priority: P1)

用户在飞书派发任务，调度会话创建任务会话后向用户通报结果。用户看到的不再是裸 id，而是「任务名称（task-20261126112301-c55e）」加上工作区，一眼能对上自己刚交的是什么任务。

**Why this priority**: 派发是最高频的入口，通知里的任务对应关系直接决定用户后续跟进的效率。

**Independent Test**: 在真实宿主上派发一个任务，检查回复中对该任务的提及同时包含标题与 task id，且按约定形式排列。

**Acceptance Scenarios**:

1. **Given** 调度会话收到新任务请求并成功创建任务，**When** 调度会话回复用户，**Then** 回复以「名称（id）」形式提及该任务，并附工作区信息。
2. **Given** 任务标题在创建后被 `task_update` 改名，**When** 调度会话再次向用户提及该任务，**Then** 名称使用台账中的当前标题。

---

### User Story 2 - 报告与状态转述按统一形式提及任务 (Priority: P2)

任务会话发来进度或提问上报、用户在网页或飞书询问任务状态、调度会话通报轮次失败与会话归档时，调度会话提及的每个任务都带名称与 id，用户无需回查台账即可对上号。

**Why this priority**: 转述与询问贯穿任务全程，形式统一才能让所有对外话术一致。

**Independent Test**: 分别触发一次上报转述、一次状态询问、一次归档通知，检查三次回复中对相关任务的提及形式。

**Acceptance Scenarios**:

1. **Given** 任务会话上报进度，**When** 调度会话向用户转述，**Then** 转述中提及该任务时使用「名称（id）」形式。
2. **Given** 用户询问「现在有哪些任务在跑」，**When** 调度会话列出任务，**Then** 列表中每个任务都以「名称（id）」形式出现。
3. **Given** 任务会话轮次失败或用户归档了会话，**When** 调度会话向用户通报，**Then** 通报中对相关任务的提及使用「名称（id）」形式。

---

### User Story 3 - 结束与取消任务的说明带上名称与 id (Priority: P3)

用户确认完成或要求取消任务后，调度会话结束任务并向用户通报结果，提及的任务同样是「名称（id）」，用户能确认结束的是哪一条。

**Why this priority**: 结束是低频终点，但形式必须与全程一致，避免最后一条消息反而无法对应。

**Independent Test**: 走一遍完成确认流程，检查结束通报中的任务提及形式。

**Acceptance Scenarios**:

1. **Given** 用户确认任务完成，**When** 调度会话调用 `task_end(completed)` 并回复，**Then** 回复以「名称（id）」形式提及该任务。
2. **Given** 用户要求取消某任务，**When** 调度会话执行并回复，**Then** 回复以「名称（id）」形式提及该任务。

---

### Edge Cases

- 接管的现有会话没有可读标题时，任务标题回退为会话 id；提及仍按「名称（id）」形式，名称位取台账中的标题（即会话 id）。
- 用户回复里只写 id 或只写名称来指认任务：现有的任务匹配规则继续生效，本需求只约束调度会话的输出，不改变用户的写法。
- 回复以简短为既有规则；「名称（id）」形式不要求追加解释语。
- 名称无法从台账或归档取得时的表述待 D-005 确认。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 调度会话向用户输出（含飞书通知与会话正文回复）提及任务时，MUST 同时给出该任务的名称与 task id，形式为「名称（id）」，分隔符写法待 D-002 确认。
- **FR-002**: FR-001 只允许的形式为「名称（id）」并列；MUST NOT 出现只写 task id 或只写名称的任务提及。
- **FR-003**: 规则 MUST 覆盖全部向用户转述场景：创建任务通知、接管任务后的回复、上报转述、状态询问与列表、轮次失败与归档通报、结束与取消通报。
- **FR-004**: 名称 MUST 取任务台账中的当前标题；id MUST 取 task id（格式 `task-yyyyMMddHHmmss-4hex`）。
- **FR-005**: 调度提示词中与「向用户提及任务」相关的现有指令 MUST 与新规则一致；与新规则冲突或仅要求「告知 task id」的表述 MUST 同步改写。
- **FR-006**: 本规则 MUST NOT 改变对用户输入的理解方式，仅约束调度会话的输出。
- **FR-007**: 桥接提醒是否纳入本规则待 D-003 确认；确认后按结论决定规则落点范围。
- **FR-008**: 提及同一任务的频率约束（每次完整或回复内首次完整）待 D-001 确认。
- **FR-009**: 测试 MUST 断言提示词含新形式，且不存在与新规则冲突的旧表述。
- **FR-010**: `docs/how-it-works.md` MUST 按现有条目风格补充该输出规则；`CHANGELOG.md` MUST 增加条目。

### Key Entities

- **任务台账记录**: 每条任务含标题、task id、状态与消息；调度会话输出中「名称（id）」的两个取值来源。
- **调度提示词段**: `sa-dispatch` 预设注册的系统提示词，规定调度会话对用户的话术。
- **桥接提醒**: 桥接会话表层注入的提醒文本，是否列入规则范围由 D-003 决定。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 实机走一遍派发、上报转述、状态询问、结束四类场景，回复中对相关任务的提及 100% 采用「名称（id）」形式，无只写 id 或只写名称的情况。
- **SC-002**: 提示词与桥接提醒（按 D-003 结论）中与新规则冲突的表述为 0 处，由自动化测试断言。
- **SC-003**: 新规则合入后，既有「回复只给结论、保持简短」的表现不下降：抽查回复不出现额外解释或铺垫语句。
- **SC-004**: `pnpm check` 与文档同步要求全部通过。

## Assumptions

- 规则落点以调度提示词为主体；除 D-003 另有结论外，不改动被管理会话侧（`send_report` 与自动上报）的行为。
- 调度提示词正文为英文，规则措辞沿用提示词现有风格；示例形式保留用户给出的中文样式。
- README 不描述对用户的话术细节，本变更不改 README。
- 接管任务标题回退为会话 id 属现有行为，视为可用名称。
